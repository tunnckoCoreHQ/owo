# Architecture

owo is a Cargo workspace of two crates: `owo-core` (`crates/core/`), the library, and `owo-cli` (`crates/cli/`), which builds the `owo` binary. Each operation loads an identity folder into memory, works on files only, and returns a typed result; the binary turns it into text or a JSON envelope. Only the binary depends on clap. See [ADR-0005](../docs/adr/0005-typed-library-api.md).

## Modules

Each module owns one job. The core (`crates/core/src/lib.rs` and the modules beside it) is the typed API, the request types and the operation list, with the MCP server (`owo_core::mcp`) and the ACP proxy (`owo_core::acp`) as consumers of that API. The binary (`crates/cli/src/`) is the CLI. The tests that run the binary are in `crates/cli/tests/`; `crates/core/tests/lib.rs` tests the library and the ACP proxy, and `crates/core/tests/mcp.rs` the MCP server, with no binary.

### Library

- `lib.rs` is the public API. `Root::open(&Select, &Env)` resolves the root, identity and project and keeps the config warnings; `Root::identity` loads the selected identity, sets its home folder and its working folder (`Identity::cwd`) from `Env`, and sets its working project (`Identity::project`) to the selected project, unchecked. `Root` has `list`, `create`, `templates`, `template`, `sync` (a `SessionSync` with `start` and `push`, for the checked identity and project, with the run size from `SyncOptions::every`, else `sync_every` from the config, else 6), `sync_done` and `sync_due` (the sessions in the root with a pending run, only those of the identity when `Select` picks one). `Identity` has one method per identity operation: `lint`, `write`, `add`, `stamp`, `index`, `resolve`, `show`, `links`, `orphans`, `context`, `context_text`, `state`, `search`, `review`, `review_done`, `soul_note`, `soul_history`, `changes`, `export_card`, `export_skill`, `export_soulspec`, and `working_project`. Each takes the request type of its operation, such as `&StateRequest`; `SessionSync::push` takes typed turns and `SyncOptions`, so the ACP proxy calls it with no text to parse. `add` (for a note), `context` and `state` use the working project and check it then, so a project that is not found fails only the calls that use it; `search` and `export_card` take their project filter in the request. The free functions are `slug`, `migrate_v1`, `entry_types`, `parse_turns` and `dry_run`, which runs typed calls with their writes kept in memory and returns the paths they would write. Arguments and results are typed: `Kind`, `Rule`, `Scope`, `Spec`, `SyncFormat` and `Turn` for the values with a fixed list, and `Bookmark`, `ReviewRecord` and `SoulChange` for the records `sync_done`, `review_done`, `soul_note` and `soul_history` return. `changes` turns `days` into the local day that many days ago. Each call returns `owo_core::Error` on failure: its `kind` (`Usage`, `Config`, `Io` or `Failed`), the whole error text, and for a failure a caller may word itself, a typed `fault`. The core text and field help name fields, never a flag, an environment variable, a command or an exit code; the CLI words a fault with its flags and the `owo` command to run next. The core parses no command line, has no exit codes, prints nothing, reads no environment variable and takes no stream of the process. Two things still come from the process: the time zone, which the local day uses, and the environment of the `git` child that `changes` and `lint` with `changed` run. A relative root, the `.owo.toml` search and a relative path in a request (the export `out` and `png`, the sync `transcript`, the migrate `path` and `out`) start at `Env.cwd`; `migrate_v1` takes that folder as an argument. The I/O uses the joined path, and a result, a bookmark or an error text shows the path as the request gives it.
- `request.rs` holds one request type per operation, such as `AddRequest`, `StateRequest` or `SyncPushRequest`, and the `Request` trait. `read` builds the request from a `Reader` and a base request, and each read declares one `Field` with its name, `Type`, help text, default, allowed values and rules (`range`, `conflicts`, `requires`); `fields` runs it to list the fields, `from_args` runs it on `Args` over the defaults, with a usage error for a value of the wrong type, and `check` runs it over a request to check the rules of its fields: a required path that is empty, a day outside the years 0000 to 9999, and the declared rules. `Args::with_path` gives a path field its raw path, which the request takes over the text; the typed function turns it into UTF-8 text (`utf8` in `lib.rs`). See [[decisions#Options are declared once in the core]]. Each request type carries its defaults in `Default`: `ContextRequest` (three project notes, as text), `StateRequest` (14 days), `SearchRequest` (10 hits), `ChangesRequest` (everything), `CardRequest` (a V3 card) and `SyncOptions` (no run size, so `SessionSync` takes `sync_every` from the config, else 6); `SyncFormat` defaults to `jsonl`. `MAX_DAYS` (36500) is the largest number of days. `Args::new` checks that each argument is a field, each required field is there and each value of a fixed list is in it. Each typed function runs `check` on its request first, a usage error with a fault (`OutOfRange`, `Conflict`, `Needs`) for a broken rule, so `lint`, `search`, `soul_history` and `resolve` return a `Result` too. See [[decisions#Options are declared once in the core]].
- `operation.rs` holds `operations()`, every operation in CLI order with its name words (`["review", "done"]`), its help line and its request type. `Operation::run` maps checked `Args` into the request (a usage error for a value of the wrong type), opens the root, makes the typed call, which checks the rules, and returns a `Ran`: the config warnings and the typed `Outcome` or the error. The caller's input stream gives the text `write` and `sync push` read when the request has none, after the root resolves; `search` and `export card` take their project filter from the `Select` the caller gives, not from the config. `Outcome::envelope` builds the `{ ok, data, warnings, errors }` `Envelope` of a result. Each operation that writes files is built with `writes`, which reads its request inside `DryRun` (in `request.rs`, the `dry-run` field), and with that field set runs the call inside `write::dry_run` and returns `Outcome::DryRun`: the outcome and the paths, with `would_write` added to the `data` of its envelope.
- `error.rs` defines `Error`, `ErrorKind` and `Fault`. A module raises a `Fault` through `anyhow`, and the `From<anyhow::Error>` conversion finds it again, so the kind and the fault reach the caller.
- `config.rs` resolves root, identity, project and KB from `Select` and `Env`, and checks the selected identity and project (a config error). See [[formats#Config resolution]].
- `identity.rs` walks one identity folder and parses every Markdown file into an `Entry` with a `Kind` decided by its path. `Kind::name` is the one name of a kind in output and `--type` values, and `Entry::label` gives the title, else the stem key.
- `markdown.rs` splits frontmatter and parses it with `serde-saphyr` into `serde_json` values, reads sections, extracts wiki-links outside code, counts words.
- `slug.rs` holds the one slug function.
- `templates.rs` embeds every template with `include_str!` and fills `{{key}}` placeholders.
- `write.rs` holds `Writes`, the one way the core writes files: a set of files and folders that `commit` writes all or none of, each file through a temporary file and a rename. See [[decisions#Writes are all or nothing]]. In a dry run (`write::dry_run`) `commit` keeps its targets in memory, and `read`, `read_to_string`, `exists` and `kept_under` give the kept files to the reads; see [[decisions#Dry run keeps writes in memory]].
- `create.rs` implements `owo new`; `add.rs` implements `owo add` and `owo write`.
- `index.rs` generates `_index.md` files and `life/timeline.md`.
- `state.rs` and `stamp.rs` hash files and maintain the three `state.json` files; `state::parse_day` is the one strict `YYYY-MM-DD` parser. Readers go through `state::doc` for a whole file, and `state::updated`, `state::stamps`, `state::history` and `state::review` for its parts, over the copies `Identity::load` reads; writers read, change and write a fresh copy.
- `lint.rs` runs the rules in [[lint]]; each rule appends findings and the runner names them after the rule.
- `find.rs` resolves names, shows sections, and lists backlinks, outlinks and orphans. `find::show` picks a `kb:` link or an entry for `owo show`, and `find::section_text` writes the one "no section" error for both. `find::unresolved` writes the one "does not resolve" error for every `find::one` caller (`show`, `links`, `context --with`, soul-note evidence, `export --scenario`); `owo resolve` gets candidates, not an error, and its envelope uses the same text; lint words its own link errors.
- `kb.rs` finds a project KB (`~/` is `Identity::home`, which `Root::identity` sets from `Env`), builds the pointer `owo context` prints, and resolves `[[kb:...]]` links for `owo show` and lint.
- `status.rs` derives current state and the Now block; `context.rs` builds the tiered load set and its text.
- `search.rs` is the BM25 ranker; `review.rs` builds the review packet, records finished reviews, and keeps the soul history.
- `git.rs` wraps the `git` binary; `changes.rs` implements `owo changes` and the changed-file set for `lint --changed`.
- `export.rs` writes character cards (JSON or PNG), SoulSpec packages and skill wrappers.
- `sync.rs` parses transcripts and writes session slices; `migrate.rs` converts v1 identities.
- `output.rs` defines `Diagnostic` and its `Level`, and `warning_line`, the one `owo: warning: <text>` line that the CLI, the MCP server and the ACP proxy write.

### MCP and ACP

- `mcp.rs` is `owo_core::mcp`, the MCP server. Its tools are the operations, and each input schema comes from the fields of the request type. `reply` answers one JSON-RPC message, `serve` answers each line of a reader on a writer, and `serve_http` answers each POST on a listener that `bind` opens. Each tool call checks its JSON arguments with `Args::new`, runs the operation with an empty input, returns the envelope, or for `context` and `show` the text, followed by the warning lines, and turns a panic into an `isError` result; see [[decisions#MCP calls the library]].
- `acp.rs` is `owo_core::acp`, the ACP proxy, a consumer of the API above, so a program that links the core can run it on streams it gives. `Proxy::new` resolves the identity and lists the identities of the root with `Root::open`, `Root::identity` and `Root::list` before the agent starts, with `Options` for the injection mode and the command line of the MCP server it adds, and a writer for warning lines. `Proxy::run` copies lines both ways on the four streams the caller gives it, changes only the lines that carry the injection, the identity picker and the `/owo` command, answers the picker and the command itself, reads the injected context with `Identity::context` and `context_text`, and stores turns per session identity with `SessionSync::push`; see [[decisions#ACP proxy passes lines through]].

### Binary

- `main.rs` connects the process to the core: it builds the clap command with `cli::command`, parses arguments, builds `Env` from the environment with `env`, finds the operation of the command, maps the matches into `Args` with `cli::args`, and runs it with the process stdin as its input. It keeps the clap command it parsed with, and prints a usage error (`Output::usage`) with `Command::error`, so it is worded as clap words its own and keeps its colour on a terminal; else it prints the two strings `Output::render` makes. Stderr gets the warnings as `owo: warning: <text>`, then a usage error as clap words it or the error line `owo: <error>`; stdout gets the JSON envelope with `--json`, else the text. For `owo mcp` it takes over stdin and stdout (`own_stdio`, `detach_stdio`) and passes the copies to `mcp::serve`, or binds with `mcp::bind`, prints the URL and calls `mcp::serve_http`. For `owo acp` it builds `owo_core::acp::Proxy` with stderr as the warnings writer and `mcp_server` (`<this binary> mcp -i <identity>`, the path from `std::env::current_exe`, else `owo`) as the MCP server command line, starts the agent process, hands its pipes and the process stdin and stdout to `Proxy::run`, stops the agent when that fails, and exits with the agent's code. It keeps the SIGPIPE handling for every command but `owo mcp` and `owo acp`, which ignore the signal.
- `cli.rs` builds the clap command from `operations()`: each operation is a command, and each field a flag or a positional argument with its help text, default, allowed values, value name, range, `conflicts_with` and `requires`, so clap gives its own help and usage text and checks the rules. The help of a field that names stdin, an exit code or another flag is the CLI's own, in `help`. A two-word operation goes under a group command; the CLI holds only the help lines of the groups (`soul`, `export`, `sync`, `migrate`), the global flags, and `mcp` and `acp`. `cli::args` turns the matches of a command into `Args`: a switch as a boolean, a field with several values as an array, else the raw text. `cli::with_paths` adds the raw value of each path field, and the core turns it into UTF-8 text.
- `render.rs` turns a `Ran` into its `Output`: the core's envelope, and without `--json` the text of the outcome and the envelope's text warnings. The text of `Outcome::DryRun` is the text of its outcome without the confirmation lines, then the `would write` lines. A failure keeps the warnings found before it. A name that does not resolve and a search with no hits also give an error line.
- `text.rs` builds the longer texts of an outcome: lint lines, tables, the review packet and the other reports, with the helpers only text output uses (the day of a stamp, a list of wiki-links).
- `output.rs` defines the exit codes and `Output`: the envelope, the text, the warnings, the error and the exit code. `Output::render` turns it into the stdout text and the stderr text, and `Output::warning_lines` gives the warnings alone. The error kind gives the exit code: a usage error 2, a config error 3, an I/O error 4, any other 1. The function `says` words each library `Fault` in the CLI's terms, from the fault and not its text: a field as its flag, such as `--until`, and the `owo` command to run, such as "; run `owo index` instead".

## Loading an identity

`Identity::load` reads `identity.json` and the three state files, then walks the folder in file-name order and parses each `.md` file once. In a dry run the `.md` files the run kept under the folder replace or join the walked ones, in the same order; see [[decisions#Dry run keeps writes in memory]].

Path decides the kind: `life/events/x.md` is an event, `life/locations/<slug>/overview.md` a location, any other file in that folder a location detail. The files `owo index` writes (`life/_index.md`, each life category `_index.md`, `work/_index.md` and `life/timeline.md`) are generated. Files outside the layout, an `_index.md` elsewhere included, get `Kind::Unknown`, which lint reports.

`classify` in `identity.rs` maps a path to its kind, and `Kind::rel` beside it maps a kind back to the path `owo add` writes. A unit test checks that `classify` returns the same kind for the `Kind::rel` path of every type `owo add` creates.

## Link resolution

Links resolve through one lowercase key map, built once in `Identity::load`, from titles, aliases, file stems (folder name for `overview.md`), identity-relative paths and soul file names.

`resolve_link` tries the raw lowercase target, then its slug. Generated files are left out of the map, so links always land on authored entries. Only `find::resolve`, for a name typed on the command line, also accepts a file path, absolute or relative to the working directory. Links in files resolve through the key map alone, so lint gives the same result from any folder.
