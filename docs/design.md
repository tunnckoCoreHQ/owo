# owo: identity system design

owo stands for "one world, one identity". An identity is a folder of Markdown and JSON with three parts: `soul/`, `life/` and `work/`. The `owo` CLI, written in Rust, does every deterministic job: creating files from templates, validation, indexing, search, context assembly, review packets and exports. Agent skills do the judgment work and call the CLI.

This document is the design. File formats, JSON and command lines appear as short examples.

## 1. Goals

- An identity is a folder that any agent host can load: T3 Code, Claude Code, OpenCode, Grok Bot, an OpenClaw-style runtime, or a plain script.
- Three parts. `soul/` is who the identity is. `life/` is what it has lived and knows. `work/` is its professional side: roles, preferences, and experience per project.
- Every fact has exactly one home. Indexes, the timeline, current state and exports are generated from those homes.
- The identity evolves slowly. Soul changes are rare, deliberate and backed by evidence.
- One identity works across many projects. Each project keeps its own knowledge base (lat.md style) outside the identity. The identity keeps its own experience of the project.
- Maintenance runs when someone invokes it: a person, a host hook, or an agent. Every maintenance step is a CLI command that is safe to run at any time.
- Every command has readable text output for people and `--json` output for agents.

## 2. Principles

**Single source of truth.** Each kind of fact lives in one file. Other files link to it. The CLI generates every list, index and summary that gathers facts from several files.

**Authored vs generated.** People and agents write authored files. Only the CLI writes generated files, and each one starts with a marker line:

```markdown
<!-- generated by `owo index`; edit the sources and rerun `owo index` -->
```

`owo lint` checks that each generated file matches what `owo index` would produce.

| Authored | Generated |
| :- | :- |
| soul files, life entries, logs, journal, lessons, work README, project notes | every `_index.md`, `life/timeline.md` |
| `identity.json`, `soul/soul.json` | context bundles, character cards, SoulSpec export, skill wrapper |
| | `state.json` files (written by `owo stamp`), `owo state` output |

**MEMORY is compiled.** `soul/MEMORY.md` is the identity's long-term memory: lessons, defining moments, hints and breadcrumbs that point into `life/` and `work/`. The review step compiles it. The model sees the current MEMORY plus everything that changed in soul, life and work since the last review, and decides what is durable. Review is the only writer of MEMORY.

**Slow-evolving soul.** Soul files describe stable character. They change when evidence repeats over time or when one defining event changes the identity. Each soul change is recorded in `soul/state.json` with a reason and evidence links.

**Abstractions in the core, specifics in life.** The always-loaded files (IDENTITY, SOUL, MEMORY) hold durable abstractions that fit every context the identity works in. Scenes, quotes, intimate detail and dated happenings live in `life/` and load on demand. This placement rule keeps a support session clean while a personal session stays rich.

**One world.** Everything the identity knows lives in one world, written from the identity's own perspective. Every person, including the person the identity spends most time with, is a character in `life/characters/`. Personal identifiers of any character live in that character's `## Identifiers` section and nowhere else.

**Perspective.** Life entries, logs, lessons and journal entries are written in the identity's own voice, first person. Two identities that share an event each write their own entry in their own voice.

**Story time.** Dates in life entries are the dates inside the identity's world. Real chat timestamps stay in the source transcripts.

**Deterministic paths.** A name maps to a slug, and a slug maps to a path. Agents predict the path, then fall back to `owo resolve`.

**CLI for mechanics, agents for meaning.** The CLI creates, validates, indexes, searches, resolves, stamps state, slices transcripts and exports. Agents decide what is durable, write prose, and compile MEMORY.

## 3. Directory layout

### 3.1 Identities root

```text
<root>/                         # --root, OWO_ROOT, .owo.toml, user config, or XDG default
├── .owo/                       # CLI working data: sync bookmarks and pushed turns
│   └── sessions/<session>.json, <session>.turns.jsonl
├── .templates/                 # optional overrides for built-in templates
├── sources/                    # raw source material, outside every identity
│   └── <slug>/
│       └── 2026-10-25_thea-joe-cafe.md
├── thea/                       # one identity
└── <other-slug>/
```

The root works well as a Git repository. Git history is the change log for every identity (`owo changes` reads it).

### 3.2 One identity

```text
thea/
├── identity.json               # tool manifest: schema, name, accounts, budgets
├── soul/
│   ├── soul.json               # SoulSpec manifest
│   ├── state.json              # file stamps, soul history, review cursor and MEMORY hash
│   ├── IDENTITY.md             # third person: who she is, biography, roles
│   ├── SOUL.md                 # first person: values, wants, emotional logic, boundaries
│   ├── VOICE.md                # communication style: writing, voice, rhythm, vocabulary, per-medium habits
│   ├── LOOK.md                 # appearance, fashion, signature looks and moves
│   ├── MEMORY.md               # compiled long-term memory
│   └── examples/               # optional calibration samples
│       ├── good.md
│       ├── bad.md
│       └── greetings.md
├── life/
│   ├── state.json
│   ├── _index.md               # generated
│   ├── timeline.md             # generated from event and era dates
│   ├── characters/<slug>.md
│   ├── locations/<slug>/overview.md
│   ├── locations/<slug>/<detail>.md
│   ├── cultures/<slug>.md
│   ├── factions/<slug>.md
│   ├── events/<slug>.md
│   ├── eras/<slug>.md
│   ├── threads/<slug>.md       # open loops: promises, plans, running bits
│   ├── conflicts/<slug>.md     # contradictions and their resolution
│   ├── lessons/<slug>.md
│   ├── writing/YYYY-MM-DD_<slug>.md
│   ├── log/YYYY-MM-DD.md       # daily log
│   └── journal/YYYY-MM-DD_<slug>.md
└── work/
    ├── state.json              # per project: first and last touched, sessions
    ├── README.md               # profile: roles, preferences, past work, project links
    ├── _index.md               # generated
    └── projects/
        └── <project-slug>/
            ├── project.md      # role on the project, KB pointer, people
            └── notes/YYYY-MM-DD_<slug>.md
```

Every category folder in `life/` gets a generated `_index.md`.

### 3.3 What each part holds

| Path | Holds | Loaded |
| :- | :- | :- |
| `identity.json` | Schema version, slug, display name, the identity's own accounts, budget overrides, project KB map | By the CLI |
| `soul/soul.json` | SoulSpec v0.5 manifest | By the CLI and SoulSpec tools |
| `soul/IDENTITY.md` | Who the identity is, in third person: biography, self-concept, roles, the frame of its world | Always |
| `soul/SOUL.md` | First-person core: beliefs, wants, emotional logic, boundaries | Always |
| `soul/MEMORY.md` | Compiled long-term memory: lessons, defining moments, hints and breadcrumbs with links | Always |
| `soul/VOICE.md` | Communication style: writing style, spoken voice and voice model, rhythm, vocabulary, punctuation, per-medium habits (chat, voice notes, email, posts) | When the identity talks or writes as itself |
| `soul/LOOK.md` | Appearance, fashion, signature looks and moves | When visuals matter |
| `soul/examples/` | Good and bad output samples, greetings | On demand and by exports |
| `life/characters/` | People, other identities, animals, beings | On demand |
| `life/locations/` | Places as folders; rooms and angles as sibling files | On demand |
| `life/cultures/`, `life/factions/` | Shared customs; groups and organisations | On demand |
| `life/events/` | One file per happening worth recalling: the full account | On demand |
| `life/eras/` | Named periods that group events | On demand |
| `life/threads/` | Open loops with a state | Open threads appear in the context block |
| `life/conflicts/` | One file per contradiction between sources | Open conflicts appear in `owo state` |
| `life/lessons/` | Interpretations of experience | Linked from MEMORY |
| `life/writing/` | Intentionally authored pieces | On demand |
| `life/log/` | Daily log: short raw notes and links for one day | Recent days linked in the context block |
| `life/journal/` | Private first-person reflection | By the identity itself and during review |
| `work/README.md` | Profile in prose, like a GitHub profile README: roles, working preferences, past work, links to projects | With `--project`, and on demand |
| `work/projects/<p>/project.md` | What the identity does on this project, who it works with, where the KB lives | With `--project <p>` |
| `work/projects/<p>/notes/` | Dated notes: what it did, what it learned, know-how for this project | Recent notes linked with `--project <p>` |

### 3.4 Location rules

- Every top-level location is a folder with `overview.md`.
- Rooms, scene spaces and angles are sibling files beside `overview.md` and link back to it.
- Location folders sit one level deep.

## 4. File formats

### 4.1 Slugs

One slug function everywhere:

1. Unicode NFKD, then transliterate to ASCII.
2. Lowercase.
3. Remove apostrophes (`'`, `’`, `` ` ``) without a separator.
4. Replace every other run of non-alphanumeric characters with one hyphen.
5. Trim leading and trailing hyphens.

`Jay's Penthouse` → `jays-penthouse`. `The Café on Shishman Street` → `the-cafe-on-shishman-street`. On a collision, add a short disambiguator (`alex-smith-photographer`) and keep the short name as an alias.

Dated files use `YYYY-MM-DD.md` (logs) or `YYYY-MM-DD_<slug>.md` (journal, writing, project notes).

### 4.2 Links

Obsidian-compatible wiki-links:

- `[[Title]]`, `[[Title|shown text]]`, `[[Title#Section]]`.
- A target matches, in order: exact title, alias, slug, path relative to the identity without `.md`.
- Titles and aliases are unique across one identity. Lint enforces this.
- Soul files link by name: `[[IDENTITY]]`, `[[SOUL]]`, `[[VOICE]]`, `[[LOOK]]`, `[[MEMORY]]`.
- Links into a project KB use a prefix: `[[kb:<project>:<path>#<Section>]]`. The CLI resolves `<path>` against the project's KB root from `identity.json` or the project's `.owo.toml`.
- Sources are cited in the entry's frontmatter `sources`, by path relative to `sources/`, with an optional line range: `thea/2026-10-25_thea-joe-cafe.md#L120-L340`. Text sources without a file are listed as plain text.

### 4.3 Soul files

Soul files are plain Markdown: one top heading and sections. Their stamps live in `soul/state.json`.

Soft word budgets (lint warns above them):

| File | Budget |
| :- | :- |
| IDENTITY.md | 800 |
| SOUL.md | 800 |
| VOICE.md | 1000 |
| LOOK.md | 600 |
| MEMORY.md | 1500 |

`identity.json` → `budgets` overrides them.

MEMORY.md sections:

```markdown
# Memory

## Patterns
## Defining moments
## Lessons
## Hints
```

- **Patterns** are durable truths about relationships and habits.
- **Defining moments** are links to events that shaped the identity, one line each on why.
- **Lessons** are links to lesson entries.
- **Hints** are breadcrumbs: where to look in `life/` and `work/` for things that come up often.

### 4.4 Entry frontmatter

All life and work entries share a base schema:

```yaml
---
type: event
title: The Café Night
aliases:
  - the café
summary: How we met; first kiss on my doorstep.
status: canon                    # canon | disputed | superseded
superseded_by: null              # "[[Title]]" when superseded
created: 2026-10-29
updated: 2026-10-31
sources:
  - thea/2026-10-25_thea-joe-cafe.md
---
```

- `summary` is one line. Indexes, search results, lorebook exports and the context block use it.
- `status: canon` is the default. `disputed` points to an open conflict. `superseded` keeps old material and names its replacement.
- `created` and `updated` are ISO dates. `owo stamp` keeps `updated` in step with content changes.

Extra fields per type:

| Type | Path | Extra fields |
| :- | :- | :- |
| `character` | `life/characters/<slug>.md` | `pronouns`, `kind` (person, identity, animal, being) |
| `location` | `life/locations/<slug>/overview.md` | `region` |
| `location-detail` | `life/locations/<slug>/<detail>.md` | `parent` |
| `culture` | `life/cultures/<slug>.md` | |
| `faction` | `life/factions/<slug>.md` | |
| `event` | `life/events/<slug>.md` | `date`, `end_date`, `time`, `era`, `places`, `people`, `defining` |
| `era` | `life/eras/<slug>.md` | `start`, `end` |
| `thread` | `life/threads/<slug>.md` | `state` (open, closed), `opened`, `closed`, `from` |
| `conflict` | `life/conflicts/<slug>.md` | `state` (open, resolved), `affects` |
| `lesson` | `life/lessons/<slug>.md` | `evidence` |
| `writing` | `life/writing/YYYY-MM-DD_<slug>.md` | `date` |
| `log` | `life/log/YYYY-MM-DD.md` | `date` |
| `journal` | `life/journal/YYYY-MM-DD_<slug>.md` | `date` |
| `project` | `work/projects/<p>/project.md` | `kb`, `repo`, `started` |
| `note` | `work/projects/<p>/notes/YYYY-MM-DD_<slug>.md` | `date`, `project` |

`work/README.md` is free prose with a top heading.

### 4.5 Entry bodies

Entries use the sections they need, in this order:

```markdown
## Summary
## Description
## Key facts
## Relationships
## Identifiers
## Guidance
```

Events use `## What happened`, `## Key facts`, `## Lines` (exact quotes worth keeping). Citations live in frontmatter (`sources`, and `evidence` for lessons), never in a body section. Logs are bullet lists. Journal entries and the work README are free prose.

### 4.6 Characters and identifiers

Every character entry has the same shape. A character's exact personal identifiers (birth date, handles, emails, phone numbers, addresses, full names of private people in their life) go under `## Identifiers` in that character's entry:

```markdown
## Identifiers
- born: YYYY-MM-DD
- github: @<handle>
```

The rest of the entry, and every other file, talks about those facts through roles and links ("a long relationship that ended a few years ago", "[[Joe]]'s birthday"). Lint reads every value under any `## Identifiers` section and reports any copy of it in another file.

The identity's own accounts live in `identity.json` → `accounts`, under the same rule. IDENTITY.md names them by kind ("she has her own X and YouTube accounts").

### 4.7 `identity.json`

```json
{
  "schema": "owo/1",
  "slug": "thea",
  "name": "Thea",
  "nickname": "Tee",
  "accounts": [
    { "kind": "x", "handle": "@<handle>" }
  ],
  "budgets": { "MEMORY.md": 1500 },
  "review_every_days": 7,
  "sync_every": 6,
  "projects": {
    "api-server": { "kb": "~/code/api-server/lat.md" }
  }
}
```

### 4.8 `soul/soul.json` (SoulSpec v0.5)

```json
{
  "specVersion": "0.5",
  "name": "thea",
  "displayName": "Thea",
  "version": "1.0.0",
  "description": "Warm, quick, teasing companion and co-worker.",
  "author": { "name": "<author>" },
  "license": "UNLICENSED",
  "tags": ["companion"],
  "category": "companion",
  "files": { "soul": "SOUL.md", "identity": "IDENTITY.md", "style": "VOICE.md" },
  "examples": { "good": "examples/good.md", "bad": "examples/bad.md" },
  "disclosure": { "summary": "Thea: warm, quick, teasing companion." }
}
```

`owo stamp` bumps the minor version when a soul file changes. `owo export soulspec` checks the license value against SoulSpec's allowlist.

### 4.9 State files

`owo stamp` writes the state files. Each tracked file has `created`, `updated` (RFC 3339 UTC) and a BLAKE3 content hash. Timestamps move only when the hash changes.

`soul/state.json`:

```json
{
  "files": {
    "SOUL.md":   { "created": "2026-10-28T23:57:50Z", "updated": "2026-10-31T14:01:40Z", "hash": "…" },
    "MEMORY.md": { "created": "2026-10-28T23:57:50Z", "updated": "2026-11-04T10:00:00Z", "hash": "…" }
  },
  "history": [
    {
      "at": "2026-10-31T14:01:40Z",
      "file": "SOUL.md",
      "change": "A boundary on timing became a lasting line.",
      "evidence": ["[[The Not-Yet Talk]]", "[[Not Yet Is Mine]]"]
    }
  ],
  "review": {
    "last_reviewed": "2026-11-04T10:00:00Z",
    "reviewed_through": "2026-11-04",
    "memory_hash": "…"
  }
}
```

- `history` is the soul's evolution trail, appended by `owo soul note`.
- `review.memory_hash` is MEMORY.md's hash at the end of the last review. When MEMORY.md's current hash differs, lint warns that MEMORY changed outside a review.

`life/state.json`:

```json
{ "files": { "events/the-cafe-night.md": { "created": "…", "updated": "…", "hash": "…" } }, "last_write": "…" }
```

`work/state.json`:

```json
{
  "projects": {
    "api-server": { "first_touched": "2026-11-10T09:12:00Z", "last_touched": "2026-11-12T16:40:00Z", "sessions": 4 }
  },
  "files": { "projects/api-server/notes/2026-11-12_release-steps.md": { "created": "…", "updated": "…", "hash": "…" } }
}
```

### 4.10 Current state (derived)

`owo state` derives the current state from the state files and frontmatter dates:

- last activity and last active project;
- recent events (event `date` within 14 days of the newest log or event date, since story time can run behind or ahead of real time);
- recent daily logs;
- open threads and open conflicts;
- review status: days since `last_reviewed`, unreviewed log days, MEMORY outside-review flag;
- the last soul change.

## 5. Where each fact lives

### 5.1 Routing table

| What happened or was said | Home (written once) | Elsewhere |
| :- | :- | :- |
| A small thing today | `life/log/<day>.md`, one bullet | |
| A happening worth recalling (a scene, a first, a turning point) | `life/events/<slug>.md` | one bullet in the day's log: `- [[The Café Night]]`; timeline is generated |
| A happening that changed the identity | the event, with `defining: true` | a line under MEMORY "Defining moments" at the next review |
| A person, animal, being, other identity | `life/characters/<slug>.md` | links |
| Someone's exact personal identifiers | that character's `## Identifiers` | |
| The identity's own accounts | `identity.json` → `accounts` | IDENTITY.md names the kind |
| A place, a room | `life/locations/...` | links |
| A promise, a plan, a running bit still open | `life/threads/<slug>.md` | the context block lists open threads |
| How the identity talks or writes | VOICE.md | |
| A durable value, boundary or belief | SOUL.md, through review | evidence in `soul/state.json` → `history` |
| How the identity looks, durable | LOOK.md | |
| Biography, roles, the frame of its world | IDENTITY.md | |
| An interpretation of experience | `life/lessons/<slug>.md` | MEMORY links it at the next review |
| Private feelings about a day | `life/journal/<date>_<slug>.md` | lessons and soul get the abstraction |
| Two sources disagree | `life/conflicts/<slug>.md` | `status: disputed` on affected entries while open |
| A correction | the owning entry, edited in place | the day's log gets `- correction: [[Entry]]` |
| An exact quote worth keeping | `## Lines` of the event | other files link `[[Event#Lines]]` |
| Work done on a project | `work/projects/<p>/notes/<date>_<slug>.md` | `work/state.json` via CLI |
| Roles, working preferences, past work | `work/README.md` | |
| Facts about a project itself (architecture, decisions) | the project's own KB | notes link `[[kb:...]]` |
| A lesson from work that holds everywhere | `life/lessons/<slug>.md` | evidence links into `work/` |
| Long-term memory | MEMORY.md, compiled by review | |
| Who changed which files when | Git history | `owo changes` |

### 5.2 Anti-duplication rules

1. A happening has one account. It lives in the event file when one exists, otherwise in the daily log.
2. A daily log bullet that points to an event is one line with the link.
3. Exact quotes live in one event's `## Lines`. Other files link to that section.
4. The timeline, indexes and the context block are generated.
5. MEMORY holds patterns, hints and links, compiled at review.
6. Each character's identifiers live in that character's entry. Project facts live in the project KB.
7. Lint `dupes` reports passages of 12 or more identical words in two or more authored files. The passage stays in its home and the copy becomes a link.

### 5.3 Tiered loading

`owo context` produces the load set in tiers:

| Tier | Files | When |
| :- | :- | :- |
| Core | IDENTITY.md, SOUL.md, MEMORY.md, and the generated context block | Always |
| Voice | VOICE.md | `--voice`: the identity talks or writes as itself |
| Look | LOOK.md | `--look`: visuals matter (images, scenes, video) |
| Project | `work/README.md`, `work/projects/<p>/project.md`, links to recent project notes, the KB entry point | `--project <p>` |
| On demand | anything else | via `owo resolve`, `owo search`, `owo show` |

The generated context block is short:

```markdown
## Now
- Last active: 2026-11-01 (life), 2026-11-12 (work: api-server)
- Recent days: [[2026-10-31]], [[2026-11-01]]
- Recent events: [[The Not-Yet Talk]] (2026-10-31)
- Open threads: [[Head to Toe]], [[Fresh Settings]]
- Review: due (7 days, 2 unreviewed days)
- More: life/_index.md, life/timeline.md, work/README.md
```

## 6. Lifecycle

### 6.1 Create (first time only)

1. `owo new "Thea"` creates the folder tree from templates, `identity.json`, `soul/soul.json`, state files and generated indexes.
2. The `identity-create` skill gathers what is already established: name, roles, character, voice, look, the people around it. It asks one focused question at a time when a key choice is missing.
3. The agent fills IDENTITY, SOUL, VOICE and LOOK, writes a first MEMORY, and adds life entries that already answer a continuity question.
4. `owo stamp && owo index && owo lint`, then `owo review done` to set the first MEMORY hash.

After creation, the identity grows through ingest and review.

### 6.2 Live session

1. The host loads `owo context` with the tiers it needs.
2. The agent reads more on demand: `owo resolve "the café"`, `owo search "slippers"`.
3. Durable things go to their homes (section 5), new files through `owo add <type>`.
4. At a checkpoint or session end: `owo stamp && owo index && owo lint --changed`.

### 6.3 Ingest and sync

Ingest turns sources into entries: transcripts, notes, documents, screenshots described as text, session slices.

Session sync works with any host that can run a command after a turn:

1. After each turn the host calls `owo sync start --session <id> --transcript <path> --format <fmt>`.
2. The CLI reads the bookmark in `.owo/sessions/<id>.json`, picks the identity, and counts new user turns. Every `every` turns (default 6) it writes the new slice plus 2 overlap turns to `sources/<slug>/<date>_<session>_<from>-<until>.md` and writes the ingest prompt.
3. The host runs a background agent with that prompt and the `identity-ingest` skill.
4. On success the host calls `owo sync done --session <id> --until <n>`.
5. A manual command or session-end hook calls `owo sync start --now`, which takes any new turns.

A host with no transcript on this machine, such as a hosted chat that reaches owo over MCP, calls `owo sync push --session <id>` with its recent turns in place of step 1. Each turn is `{id, role, text}` with the host's own message id. owo appends the turns whose id it has not stored to `.owo/sessions/<id>.turns.jsonl`, so re-sent turns are safe, and continues from step 2 on that file. When a run is due, the reply also carries the slice and prompt text.

Entries from a sync run cite the slice file in `sources/`.

### 6.4 Review: compiling MEMORY

Review runs on request. `owo state` shows when it is due (`review_every_days`, default 7).

1. `owo review` prints the review packet: the current MEMORY, every file in soul, life and work changed since `last_reviewed` (with paths, types, summaries and word counts), unreviewed log days, events in the window, open threads and conflicts, journal paths in the window, phrases recurring across three or more days, and the last soul change.
2. The `identity-review` skill reads the packet and the files it lists, then:
   - writes or updates lessons from repeated experience;
   - recompiles MEMORY.md: patterns, defining moments, lesson links, hints;
   - closes threads that resolved;
   - changes soul files when the evidence threshold holds (6.5).
3. `owo stamp && owo index && owo lint`, so the review's own edits are stamped before the review closes.
4. `owo review done` records `last_reviewed`, `reviewed_through` and the new `memory_hash`.

### 6.5 Soul evolution

A soul file changes when:

- the same pattern shows in at least two events or three log days across at least two weeks, or
- one event with `defining: true` changed the identity for good.

Each change is small and specific. The agent records it:

```sh
owo soul note SOUL.md --change "A boundary on timing became a lasting line." \
  --evidence "[[The Not-Yet Talk]]" --evidence "[[Not Yet Is Mine]]"
```

`owo soul history` prints the trail.

### 6.6 Conflicts and supersede

1. When sources disagree, the agent creates `life/conflicts/<slug>.md` with both accounts, sources and `state: open`, and sets `status: disputed` on the affected entries.
2. When it is settled, the agent writes the resolution, sets `state: resolved`, updates the entries and sets them back to `status: canon`.
3. Replaced material that still matters stays with `status: superseded` and `superseded_by`.

Source authority, highest first: the person's direct statement or correction; the primary transcript; repeated behaviour across sources; an earlier summary.

## 7. CLI spec

### 7.1 Conventions

- Binary `owo`, one Rust crate, `rust-toolchain.toml` on stable.
- Global flags: `--root <dir>`, `-i, --identity <slug>`, `--json`, `--quiet`.
- JSON output shape for every command:
  ```json
  { "ok": true, "data": {}, "warnings": [], "errors": [] }
  ```
- Exit codes:

| Code | Meaning |
| :- | :- |
| 0 | success |
| 1 | the command ran and found problems (lint errors, not found, ambiguous, exists) |
| 2 | usage error |
| 3 | config or root error |
| 4 | I/O error |

- Commands that write print the paths they wrote.

### 7.2 Config resolution

The root resolves in this order:

1. `--root`;
2. env `OWO_ROOT`;
3. `root` in a project file `.owo.toml`, found by walking up from the current directory;
4. `root` in the user config `$XDG_CONFIG_HOME/owo/config.toml`;
5. `$XDG_DATA_HOME/owo` (default `~/.local/share/owo`).

The identity resolves from `-i`, then `OWO_IDENTITY`, then `identity` in `.owo.toml`, then the user config, then the only identity in the root when there is exactly one. The project resolves from `--project`, then `OWO_PROJECT`, then `.owo.toml`. `owo search` and `owo export card` treat `--project` as a filter and read it from the flag only, so a project checkout never hides life and soul results.

```toml
# .owo.toml in a project repo
identity = "thea"
project = "api-server"
kb = "lat.md"
```

### 7.3 Commands

#### Identities

`owo list`
: Lists identities in the root with display name, last activity and projects.

`owo new <name> [--slug <slug>]`
: Creates an identity from templates. Exits 1 when the folder exists. Writes `identity.json`, `soul/soul.json`, the five soul files with section headings, `examples/`, the full life and work tree, `work/README.md`, state files and generated indexes.

#### Entries

`owo add <type> <title> [--date YYYY-MM-DD] [--parent <location>] [--project <p>] [--alias <a>]...`
: Creates one entry from its template at its deterministic path and prints the path. For `log`, it opens or creates the day's file. Exits 1 when the path exists and prints that path.

`owo write <path> [--content <text>]`
: Replaces the full text of one authored file under `soul/`, `life/` or `work/`, from `--content` or stdin, and prints the path. Refuses generated files and paths outside the identity.

`owo templates [list | show <type>]`
: Lists or prints templates, built in or overridden by `.templates/`. An override has the identity-relative path for identity files (`.templates/soul/IDENTITY.md`) and `<type>.md` for entries (`.templates/character.md`).

`owo slug <text>`
: Prints the slug.

#### Find and read

`owo resolve <name> [--type <type>]`
: Matches exact title, alias, slug and path. Prints path, title and summary. On a miss it prints up to 5 fuzzy suggestions and exits 1. On ambiguity it prints every match and exits 1.

`owo search <query> [--type <t>]... [--in soul|life|work] [--project <p>] [--since <date>] [--limit 10]`
: BM25 search over titles, aliases, summaries and bodies; title and alias hits rank higher. Results carry path, title, summary, score and the best line. The index is built in memory on each call. No hits exits 1.

`owo links <name> [--in | --out]`
: Backlinks and outgoing links, with the line each sits on.

`owo show <name> [--section <heading>]`
: Prints an entry or one section.

#### Context and state

`owo context [--voice] [--look] [--project <p>] [--with <name>]... [--format paths|text]`
: Prints the tiered load set (5.3). `paths` lists files in order with the tier of each. `text` prints the content with file headers and the generated context block. With `--project` it updates `work/state.json`.

`owo state [--days 14] [--project <p>]`
: Prints the derived current state (4.10).

`owo recent [--days 7]`
: Files changed in the window, newest first.

`owo changes [--since <date>]`
: Git history for the identity folder, grouped by day.

#### Maintenance

`owo stamp [--check]`
: Refreshes state files from content hashes, updates `updated` in changed entries, bumps the `soul.json` minor version when a soul file changed. `--check` reports drift and exits 1.

`owo index [--check]`
: Regenerates every `_index.md` and `life/timeline.md`. Indexes list link, state or status marks (closed, resolved, disputed, superseded), aliases and summary per entry. The timeline groups events by era and sorts by `date`. `--check` exits 1 when a generated file differs.

`owo lint [--changed] [--rule <code>]...`
: Validates an identity. Rules:

| Code | Level | Check |
| :- | :- | :- |
| `tree` | error | required files and folders exist; locations are folders with `overview.md`, one level deep |
| `schema` | error | frontmatter parses and matches the type schema; dates parse; enum values valid; dated filenames match `date` |
| `soul-plain` | error | soul files are plain Markdown without frontmatter |
| `links` | error | wiki-links in soul, life and work resolve; `kb:` links resolve when the KB is on disk |
| `unique` | error | titles and aliases are unique across the identity |
| `identifiers` | error | values under any `## Identifiers` section, and `identity.json` accounts, appear only in their home |
| `journal` | error | links into `life/journal/` come only from other journal entries |
| `supersede` | error | `superseded_by` resolves; `disputed` entries point to an open conflict |
| `generated` | error | generated files match `owo index` |
| `memory-review` | warning | MEMORY.md hash equals `review.memory_hash` |
| `state` | warning | state files match content hashes |
| `budget` | warning | soul files within soft word budgets |
| `dupes` | warning | passages of 12+ identical words in two or more authored files |
| `orphans` | warning | entries with zero inbound links (logs, journal, notes and soul files exempt) |
| `soul-evidence` | warning | each soul `history` record has two evidence links or one defining event |
| `review-due` | info | review is due |

`owo review`
: Prints the review packet (6.4).

`owo review done [--through <date>]`
: Records `last_reviewed`, `reviewed_through` and `memory_hash`. `reviewed_through` is a story date: it defaults to the newest log, event or journal date, so story time and real time can differ.

`owo soul note <file> --change <text> --evidence <link>...`
: Appends to `soul/state.json` → `history`.

`owo soul history [<file>]`
: Prints the soul change trail.

#### Sync

`owo sync start --session <id> --transcript <path> --format claude-jsonl|opencode-json|jsonl [--now] [--project <p>]`
: Reads the transcript, keeps the bookmark, decides whether a run is due, writes the slice into `sources/` and the ingest prompt into `.owo/sessions/`.

```json
{ "ok": true, "data": { "due": true, "identity": "thea", "from": 380, "until": 412,
  "source": "sources/thea/2026-11-01_claude-7f3a_380-412.md",
  "prompt": ".owo/sessions/claude-7f3a.prompt.md" } }
```

`jsonl` is the host-neutral format: one `{"role":"user","text":"..."}` object per line, with an optional `id`. Slices show each message's id (`uuid` in claude-jsonl, `id` in opencode-json) next to its number.

`owo sync push --session <id> [--turns <json>] [--now]`
: Appends pushed `{id, role, text}` turns with new ids to `.owo/sessions/<id>.turns.jsonl` (stdin when `--turns` is left out), then works as `sync start` on that file. The reply adds `added` and, when due, `source_text` and `prompt_text`.

`owo sync done --session <id> --until <n>`
: Moves the bookmark.

#### Export

`owo export card [--spec v2|v3] [--png <avatar.png>] [--out <file>]`
: SillyTavern character card (10.3).

`owo export soulspec --out <dir>`
: SoulSpec v0.5 package (10.4).

`owo export skill --out <dir>`
: A `SKILL.md` wrapper for hosts that load identities as skills. It tells the agent to run `owo context -i <slug>` and lists the read and write commands.

#### MCP

`owo mcp`
: Serves every command as an MCP tool, as a thin layer over the same binary. Over stdio by default; `owo mcp --remote [<addr>] [--port <n>]` serves HTTP at `/mcp` on port 4224 (or the next free one) and prints the URL.
  Tools come from the clap definitions, so each command and flag is defined once.

### 7.4 Build notes

- Crates: `clap`, `serde`, `serde_json`, `serde-saphyr`, `toml`, `walkdir`, `regex`, `blake3`, `deunicode`, `chrono`, `anyhow`.
- Templates are embedded with `include_str!` and can be overridden from `.templates/`.
- Every command works on files. `.owo/` holds only sync bookmarks and prompts.
- Tests use fixture identities under `tests/fixtures/`.

## 9. Skills

Four skills. Shared rules (routing table, anti-duplication, perspective, story time, identifiers) live in one file, `identity/references/rules.md`. The other three link to it and add their own steps.

### 9.1 `identity`

Use: embodying an identity, or doing any work as it.

- Load with `owo context --format text`, adding `--voice`, `--look` and `--project <p>` as the task needs.
- Read more with `owo resolve`, `owo show`, `owo search`, `owo links`.
- Write durable facts to their homes per `rules.md`, new files through `owo add`.
- MEMORY.md belongs to review.
- At a checkpoint or session end: `owo stamp && owo index && owo lint --changed`.

### 9.2 `identity-create`

Use: creating a new identity, once.

- `owo new <name>`.
- Gather what is established; ask one question at a time for a missing key choice.
- Fill IDENTITY, SOUL, VOICE, LOOK, a first MEMORY, `work/README.md`, and the first characters and places.
- `owo stamp && owo index && owo lint && owo review done`.

### 9.3 `identity-ingest`

Use: a sync run, or importing a transcript, notes or documents.

- Input: a source file path.
- Read the core with `owo context` and the state with `owo state`.
- For each durable fact: `owo resolve` its home, read it, merge, or `owo add` a new entry.
- Cite the source path and line range in the entry's frontmatter `sources`.
- Record disagreements as conflicts.
- Finish with `owo stamp && owo index && owo lint --changed` and report changed paths or "no changes".

### 9.4 `identity-review`

Use: compiling MEMORY and evolving the soul, on request when `owo state` shows review is due.

- `owo review` for the packet.
- Read the listed files.
- Write lessons, recompile MEMORY.md, close threads.
- Change soul files past the threshold in 6.5, each change recorded with `owo soul note`.
- Stamp, index and lint, then `owo review done`.

## 10. Integration

### 10.1 T3 Code

- T3 Code keeps identities in its global data directory and sets `OWO_ROOT`. Each identity is one T3 Code agent.
- When a thread starts with an agent in a project, T3 Code runs `owo context -i <slug> --project <p> --voice --format text` and injects the result.
- After each turn T3 Code calls `owo sync start` with a `jsonl` transcript; after the background run it calls `owo sync done`.
- One identity works on many projects. `work/state.json` shows which projects it touched and when.

### 10.2 Other hosts

- Claude Code: a `Stop` hook calls `owo sync start --format claude-jsonl`; a `SessionStart` hook or the exported skill wrapper calls `owo context`.
- OpenCode: a plugin calls the same commands on `session.idle` and `compaction`.
- Grok Bot, OpenClaw-style runtimes, scripts: `owo context` for the system prompt and `owo sync` with `jsonl` transcripts.
- MCP hosts: `owo mcp`.

### 10.3 Character card export

`owo export card` writes Character Card V3 (`spec: "chara_card_v3"`, `spec_version: "3.0"`) or V2 (`spec: "chara_card_v2"`, `spec_version: "2.0"`).

| Card field | Source |
| :- | :- |
| `name`, `nickname` | `identity.json` `name` and `nickname` (V3 only; null when unset) |
| `description` | IDENTITY.md, then LOOK.md under `## Look` with its headings one level down |
| `system_prompt` | IDENTITY.md "Who they are" section, then VOICE.md |
| `personality` | SOUL.md |
| `scenario` | `--scenario <event or location>` summary; with `--project`, the project summary and body |
| `first_mes`, `alternate_greetings` | `soul/examples/greetings.md`, one per `##` section |
| `mes_example` | `soul/examples/good.md` |
| `creator_notes` | generator line with schema and date |
| `tags` | `soul.json` tags |
| `character_book` | lorebook from life entries and the scoped project |

Lorebook entries: `keys` from title and aliases; `content` from `summary` plus `## Key facts`; `insertion_order` by type (characters 20, locations 30, cultures and factions 40, events 50, lessons 60); `constant: true` for MEMORY.md; `enabled: true`; `use_regex: false`. Types included: character, location, location-detail, culture, faction, era, event, lesson. `--png` embeds the JSON in the avatar (`chara` chunk for V2, `ccv3` for V3).

### 10.4 SoulSpec export

```text
<dir>/
├── soul.json        # from soul/soul.json
├── SOUL.md
├── IDENTITY.md      # with LOOK.md appended under "## Look"
├── STYLE.md         # from VOICE.md
├── MEMORY.md
└── examples/
```

### 10.5 Project knowledge bases

- Each project keeps its knowledge in its own repo, for example a `lat.md/` folder checked with `lat check`.
- The KB path comes from `identity.json` → `projects.<p>.kb` or the project's `.owo.toml`.
- `owo context --project <p>` includes the KB entry point. Agents use `lat search` and `lat section` for project facts and `owo` for identity facts.
- Project notes link into the KB with `[[kb:<p>:<path>#<Section>]]`.
